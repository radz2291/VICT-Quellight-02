# Durable memory care

`src/lib/server/memory/care-actions.ts` implements the declared `memory.correct`, `memory.forget`, `memory.resume` and `memory.retry` actions. Owner/session authorization belongs to the route; the implementation independently checks the actor's data-write scope, conversation ownership, strict action input, expected authority revision and selected original native source IDs. Archived conversations retain care access.

Correction stores the owner's full edited personal memory as the protected native override. Forget adds selected original IDs to source exclusions while preserving an independently edited personal profile; the confirmation explains that profile text can be edited separately. Resume releases only that override and preserves exclusions. Native C12 also quarantines generated assistant/tool text from older authority revisions, including late replies. Original transcripts remain intact. None of these actions invokes a model or approves individual automatic memories.

The private `memory_care_commands` diary has one unfinished command per owner, including blocked commands. It captures immutable action input, effective settings, stable native operation ID and deterministic intended authority revision before calling native mutation. The owner lease is renewable infrastructure ownership. Each actual try has a fresh declared outer VICT capability/run; native mutation has its separate real governed write receipt. The SQL fence is held only for short admission/finalization transactions, never across native work. This works with a database pool of one connection.

After native authority is confirmed, one product transaction supersedes old pending jobs and enqueues cleanup plus eligible per-conversation rebuilding under current settings. Only conversations with the current native-v2 import marker receive rebuild jobs; untouched legacy transcripts are neither imported nor queued by care. The action result confirms authority and queued work; it does not claim physical cleanup or new observations completed. `memory.retry` changes only eligible blocked/retryable jobs at the same authority, retaining their operation, source and configuration identities. If a pending Retry later encounters a different authority, it becomes blocked instead of retrying indefinitely.

`executeMemoryCareAction(stores, owner, actionId, input, commandKey)` returns `{ok,value,replay}`. `processPendingMemoryCare(stores, deadlineEpochMs)` resumes due pending/retryable commands from stored input after a browser or worker disappears. The deadline controls admission of another short keyless command, not inference duration. The dispatcher runs this before ordinary memory jobs. Scheduler eligibility is `state IN ('pending','retryable') AND wake_after<=now() AND (claim_expires IS NULL OR claim_expires<=now())`.

The command's native operation ID and intended authority stay unchanged after a lost acknowledgement. A later real attempt can recover it without repeating an authority change. Older interrupted/failed runtime receipts are not marked completed. An applied diary result can be returned idempotently even if its HTTP acknowledgement was lost. New commands first reconcile unfinished earlier work, preserving serial owner intent. If an out-of-band authority revision makes the old result unknowable, the diary stays blocked and a divergent new care command is refused; no success is invented. Inspection must distinguish pending, retryable, blocked and applied from cleanup completion.

`memory_care_attempts.attempt_id` is the real outer VICT run ID. Its completed marker is written only after the runtime confirms completion. Runtime receipts remain authoritative if a process dies between runtime completion and this operational marker. Diary/attempt tables have RLS, no PUBLIC access and only explicit private runtime grants.
